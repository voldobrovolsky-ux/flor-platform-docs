# ADR-0001 — Исправить дефекты гейтов стандарта, найденные аудитом раздела 9

## Контекст

При выводе исполняемых гейтов из FLOR-ADS §9 проведён аудит (метод и полный
протокол — `guides/gates.md`, раздел 6): каждая строка §9 проверена на
исполнимость, каждое «обязан» разделов §2, §5, §11 — на наличие гейта.
Найдено девять дефектов Д-1…Д-9; семь из них (Д-1…Д-7) требуют правки текста
стандарта, которая возможна только через экосистемное решение (FLOR-ADS §11).
Д-8 и Д-9 правки не требуют — они закрываются инфраструктурой и инструментами
и уже учтены реестром недостающих проверок в `guides/gates.md`.

Пока настоящее решение имеет статус `Proposed`, стандарт действует в текущей
редакции; валидатор `golden-path/` реализует гейты по действующему тексту.

## Рассмотренные варианты

1. **Ничего не править, компенсировать валидатором** — валидатор молча проверял
   бы больше, чем требует стандарт. Плюс: без переходного периода. Минус:
   норма и проверка расходятся; проверка без нормы — самодеятельность, которую
   любой проект вправе оспорить. Отклонён.
2. **Точечная поправка §2.2, §5.2, §5.14, §9** — правится только найденное.
   Плюс: минимальный объём, каждый пункт трассируется в дефект аудита. Минус:
   мажорная версия из-за новых блокирующих гейтов. **Выбран.**
3. **Ревизия стандарта целиком (v2.0 с пересмотром структуры)** — плюс: можно
   заодно пересмотреть спорное; минус: объём без запроса, переходный период
   по всем проектам, смешение «чиним найденное» с «улучшаем всё». Отклонён.

## Решение

Внести в FLOR-ADS следующие правки (нумерация — по дефектам аудита):

1. **Д-1, явная пустота зависимостей.** В §5.2 и строку §9 про
   `catalog-info.yaml`: пустой список зависимостей объявляется явно
   (`dependsOn: []`); отсутствие ключа — нарушение. Аналогично для
   `providesApis`, `consumesApis`.
2. **Д-2, область действия дефолта тира.** В §2.2: трактовка «нет аннотации →
   Tier 1» действует для каталога сервисов при чтении незарегистрированного
   или ещё не приведённого в соответствие компонента; внутри репозитория гейт
   §9 требует явной аннотации всегда.
3. **Д-3, машинный признак класса поля.** В §5.14: словарь данных обязан нести
   машиночитаемую пометку класса каждого поля (формат пометки выбирает
   `golden-path/` и фиксирует валидатором); гейт §9 переформулируется:
   «поле, помеченное `personal`/`sensitive` в схеме или словаре, отсутствует
   в списке маскируемых `10-operations.md`» — проверяемо сверкой двух перечней.
4. **Д-4, гейт матриц полноты.** В §9 добавить строку: «Каждая матрица
   переходов в `03-runtime.md` сопровождается матрицей полноты; пустая ячейка
   матрицы полноты — блок для T0/T1, предупреждение для T2».
5. **Д-5, трассируемость фитнес-функций.** В §9 добавить строку: «Каждое
   правило из „Правил зависимостей" `02-containers.md` имеет строку в таблице
   фитнес-функций `09-testing.md` — блок для T0/T1, предупреждение для T2».
6. **Д-6, актуальность индекса решений.** В §9 добавить строку: «`docs/decisions/index.md`
   соответствует содержимому каталога решений (перегенерация меняет файл —
   блок)».
7. **Д-7, парность языковых версий стандарта.** В §11 добавить гейт
   экосистемного репозитория: изменение `standards/ARCHITECTURE-STANDARD.ru.md`
   без изменения `.en.md` в том же изменении (и наоборот) — блок.

Версия стандарта при принятии: **2.0** — добавляются блокирующие гейты, это
ужесточение с переходными периодами по §11 (Tier 0 — 60 дней, Tier 1 — 90,
Tier 2 — до следующего значимого изменения).

## Последствия

Что проще: валидатор реализует ровно то, что написано в §9, — без молчаливых
расширений; проекты узнают о требованиях из стандарта, а не из падений CI.
Что сложнее: мажорная версия обязывает вести переходный период и уведомить
владельцев проектов. Возникший долг: механизм пометки классов полей (пункт 3)
требует выбора формата — до выбора гейт Д-3 остаётся в недостающих проверках
`guides/gates.md` с условием появления «принятие настоящего решения».

## Проверка

После принятия: гейты пунктов 4–6 реализуются валидатором
`golden-path/validator/check-docs.sh`; гейт пункта 7 — проверкой парности в CI
настоящего репозитория (валидатор уже несёт её как собственную проверку
репозитория — при принятии она получает статус гейта стандарта). До принятия
ничего из перечисленного нормой не является; расхождение между настоящим
текстом и стандартом читается в пользу стандарта.
