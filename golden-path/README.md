# Золотой путь

Опорный шаблон проекта: скелет репозитория, конвейер, валидатор документации.
Основной вход для агентных пайплайнов при заведении нового проекта.

Нормативная база: FLOR-ADS §3 — структура, §4 — матрица обязательности, §9 —
гейты. Валидатор реализует карту гейтов из `guides/gates.md`; контуры сборки
и отладки — по `guides/build-and-debug.md`.

---

## 1. Правило

**Новый проект Flōr Group стартует с копии золотого пути, а не с пустого
репозитория.** Скелет несёт все обязательные пути §3 — на них завязаны CI-гейты
и навигация TechDocs; переименование и перенос перечисленных путей запрещены
стандартом.

## 2. Состав

| Путь | Что это |
|---|---|
| `skeleton/` | Полный скелет репозитория Tier 1: корневые файлы, `docs/` по §3, devcontainer, конвейер, compose-контур отладки |
| `validator/check-docs.sh` | Валидатор документации: исполняемая сторона гейтов §9 (режимы `--project` и `--ecosystem`) |

Конвейер живёт внутри скелета (`skeleton/.github/workflows/ci.yml`): сборка
в dev-контейнере через `devcontainers/ci` (README экшена прочитан — `runCmd`
выполняется внутри собранного контейнера) плюс job `docs-gates`, зовущий
валидатор.

## 3. Процедура заведения проекта

1. **Скопируй** содержимое `skeleton/` в корень нового репозитория.
2. **Заполни плейсхолдеры** `<…>`: имя, владелец, тир в `catalog-info.yaml`
   (тир по критериям FLOR-ADS §2; сомнение трактуется в сторону строгого).
3. **Наполни `docs/`** по процедурам: уровень и файл — `guides/doc-levels.md`,
   спецификации — `guides/write-spec.md`, пришедший материал —
   `guides/decompose.md`. Артефакт, который не применим, получает явное
   «Не применимо: <причина>» — правило нуля §4.
4. **Прогони валидатор локально**: `check-docs.sh --project`. Свежая копия
   честно красная ровно по одному гейту — «обязательный артефакт в статусе
   Draft»: перевод документов в `Accepted` — акт владельца (П-2), он и есть
   гейт готовности проекта (§10.2). Остальные проверки на свежем скелете
   зелёные; красное что-то ещё — дефект заполнения.
5. **Первый инкремент** — по `guides/increment.md`, с гейтом, объявленным
   до начала.

## 4. Валидатор

Запуск: `check-docs.sh --project [--base REF]` в репозитории продукта,
`check-docs.sh --ecosystem [--base REF]` в `flor-platform-docs` (CI настоящего
репозитория гоняет его на каждом изменении). `--base` включает дифф-проверки
«в том же изменении» (контракт↔журнал, парность ru/en); без базы они
пропускаются с явной пометкой, а не молча.

Валидатор реализует **действующий** текст §9; что именно каждая проверка ловит
и каких проверок пока нет — карта и реестр недостающих в `guides/gates.md`
(П-5: здесь не дублируются). Поправки `decisions/ADR-0001` вступают в силу
после принятия решением владельца.

## 5. Самопроверка валидатора

Валидатор гоняется на самом себе: `flor-platform-docs` в режиме `--ecosystem` —
собственный CI (`.github/workflows/docs-gates.yml`); свежая копия `skeleton/`
в режиме `--project` — на выходе только «обязательный артефакт в статусе Draft»
(перевод в `Accepted` — акт владельца, §10.2), ни одного другого нарушения.
Так проверяется, что валидатор не выдаёт ложных срабатываний на собственном
эталоне, до того как его запустят на реальном проекте.

## 6. Чего здесь нет

Смысл каждого гейта и диагностика красного — `guides/gates.md`. Требования
к содержанию файлов скелета — FLOR-ADS §5 (скелет несёт только каркас
и напоминания). Скелет отражает Tier 1; для Tier 0 добавь артефакты по §4
(`asyncapi.yaml` и `pacts/` уже в скелете), для Tier 2 — сокращай по матрице,
а не на глаз.
