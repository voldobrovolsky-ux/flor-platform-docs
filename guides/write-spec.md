# Составление спецификации

Спецификация — документ, по которому агент или разработчик реализует систему,
не задавая вопросов. Каждый заданный при реализации вопрос — дефект спецификации,
и закрывается он правкой документа, а не ответом в переписке.

Нормативная база — FLOR-ADS (`standards/ARCHITECTURE-STANDARD.ru.md`): §5.6 —
обязательные матрицы поведения, §5.7 и приложение A — формат решений, §5.11–5.12 —
контракт раньше кода, §7 — заголовок и статусы документа. На каком уровне и в каком
файле спецификация живёт — `guides/doc-levels.md`. Исполняемая процедура — скилл
`/spec`; источник истины — настоящий раздел, при расхождении действует он.

---

## 1. Правило

**Спецификация готова к передаче, когда в ней нет неявного: каждое поведение
накрыто матрицей, каждое решение имеет статус, каждое неизвестное оформлено узлом
или слотом, а не пропущено молча.** Передача в реализацию — только в статусе
`Accepted` (П-2: черновик не реализуется); перевод в `Accepted` — отдельное
действие владельца, а не следствие того, что текст дописан.

---

## 2. Три вида неизвестного

Спецификация обязана различать три пометки. Смешение — типовой источник догадок,
оформленных как решения (П-1).

| Пометка | Что это | Что делает реализующий |
|---|---|---|
| `[узел]` | Решение требуется извне: владелец, бюджет, доступ, правовое основание | Не реализует эту поверхность. Полный порядок работы с узлами — `guides/open-nodes.md` |
| `[слот]` | Именованный внешний контракт, который спецификация не проектирует, а только называет: имя, направление, кто владелец | Реализует свою сторону до границы слота; сам контракт проектируется отдельно (процедура — скилл `/contract-audit`) |
| `[дефолт]` | Разумный выбор по умолчанию, владелец может изменить | Реализует, помечая как обратимое |

Статусы решений `[РЕШЕНО]` / `[дефолт]` / `[узел]` — словарь в `CLAUDE.md` §3;
здесь он не переопределяется. `[слот]` — не статус решения, а граница объёма:
слот законен в принятой спецификации, узел — нет.

---

## 3. Процедура

**Шаг 0 — режим.** Определи по входу, не спрашивая:

- есть документ и список дыр после ревью → **дополнение**: закрываются только
  перечисленные дыры, остальные формулировки не трогаются;
- есть документ без ревью → задать владельцу один вопрос: дополнить или
  переписать; до ответа — режим не выбран;
- документа нет → **создание** по шагам ниже.

Точка решения: при сомнении выбирается наименее разрушительный режим —
дополнение бьёт переписывание, переписывание бьёт создание.

**Шаг 1 — контекст и границы.** До первого раздела ответь письменно:
что именно документируем (экран, модуль, API, автомат); кто читатель (агент,
разработчик, заказчик — формат разный); что уже задокументировано — на это
ссылаемся, не дублируем (П-5); какие внешние системы затронуты — каждая
становится слотом или ссылкой на существующий контракт.

**Шаг 2 — структура по типу.** Для экрана или кабинета: положение в навигации,
режимы и условия переключения, конечный автомат с матрицами по FLOR-ADS §5.6,
что и когда фиксируется как сигнал, разрез владения (кто что настраивает),
внешние контракты слотами, открытые узлы. Для API или сервиса: входной контракт
(схема, типы, валидация), логика обработки, выходной контракт, коды ошибок
и поведение при сбое, логирование.

**Шаг 3 — реестр решений.** Каждое архитектурное решение спецификации — строка
с номером и статусом. Решение со статусом `[РЕШЕНО]`, затрагивающее триггеры
FLOR-ADS §5.7, оформляется отдельным ADR по приложению A стандарта — с разделом
«Рассмотренные варианты» и разделом «Проверка». Происхождение формата — MADR:
прочитанный шаблон требует раздел Confirmation — как подтверждается соблюдение
решения; это тот же принцип, что П-4.

**Шаг 4 — узлы, отложенное, критерии готовности.** Отдельными разделами:
реестр узлов (каждый — что требуется и от кого); отложенное — что сознательно
не делается сейчас и **условие введения** (условие — часть решения об отказе,
отложенное без условия — просто забытое); критерии готовности — «когда
[условие] — этап закрыт», по одному на каждое ключевое поведение.

**Шаг 5 — раскладка.** Спецификация, написанная единым документом, обязана
объявлять соответствие своих разделов файлам канонической структуры FLOR-ADS §3 —
таблицей в начале документа. При заведении репозитория разделы разносятся по
этим файлам; до того таблица делает будущий перенос механическим.

---

## 4. Требования к содержанию

- **Автомат без матриц не принимается.** Каждый конечный автомат сопровождается
  матрицей переходов и матрицей полноты по FLOR-ADS §5.6. Дыра в поведении видна
  как пустая ячейка; терминальное состояние без обоснования — дыра.
- **Перечисление без поведения не принимается.** Любая enum-таксономия (роли,
  типы, статусы) — матрицей `значение → поведение` по всем измерениям, где
  поведение различается (FLOR-ADS §5.6).
- **«Обязан» без проверки — «желательно»** (П-4). В том же документе: ссылка на
  проверку либо строка в реестре недостающих проверок с условием появления.
- **Контракт раньше кода** (П-3, FLOR-ADS §5.11): спецификация интерфейса
  меняется до реализации; спека, дописываемая по факту реализации, — протокол,
  а не контракт.
- **Таблица, а не проза, для всего перечислимого.** Прозой — почему; таблицей —
  что. Проза с перечислением внутри — место, где потеряется элемент.

## 6. Проверка

Исполняемая проверка структуры спецификации — запускается на файле спеки:

```bash
#!/usr/bin/env bash
# spec-lint <файл.md>: структурные инварианты спецификации
set -euo pipefail
f="$1"; status=0
# 1. заголовок и статус документа обязательны (FLOR-ADS §7.1)
head -1 "$f" | grep -qx -- '---' || { echo "нет YAML-заголовка"; status=1; }
grep -qE '^status: (Draft|Accepted|Superseded|Deprecated)' "$f" \
  || { echo "нет поля status"; status=1; }
# 2. матрица переходов без матрицы полноты — дыра (FLOR-ADS §5.6)
t=$(grep -c 'Матрица переходов' "$f" || true)
p=$(grep -c 'Матрица полноты' "$f" || true)
[ "$t" -le "$p" ] || { echo "матриц переходов $t, матриц полноты $p"; status=1; }
# 3. принятая спека не содержит открытых узлов (П-2 + §17 IDP-SPEC как прецедент)
if grep -qE '^status: Accepted' "$f" && grep -q '\[узел\]' "$f"; then
  echo "status: Accepted при открытых [узел]"; status=1
fi
# 4. критерии готовности обязательны ([Кк]: grep -i не сворачивает кириллицу в C-локали)
grep -qE '[Кк]ритерии готовности' "$f" || { echo "нет критериев готовности"; status=1; }
exit $status
```

Проверка входит в валидатор золотого пути (`golden-path/`).

**Недостающие проверки** (П-4, с условием появления):

| Что не ловится | Почему | Условие появления |
|---|---|---|
| Пустая ячейка внутри матрицы полноты | Нужен парсер Markdown-таблиц, grep не достаточен | Валидатор `golden-path/` получает табличный парсер |
| «Обязан» без ссылки на проверку в том же документе | Связь «требование → проверка» семантическая | До появления парсера — ручное ревью; строка о каждом непокрытом «обязан» заводится в самом документе |

## 7. Чего в этом разделе нет

Разбор чужого монолитного материала на разделы — `guides/decompose.md`. Ведение
реестра узлов после передачи спеки — `guides/open-nodes.md`. Проектирование
контракта, закрывающего слот, — скилл `/contract-audit`. Требования к содержанию
каждого файла канонической структуры — FLOR-ADS §5.
