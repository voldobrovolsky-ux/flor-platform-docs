# Паспорт элемента

Рекомендация владельца экосистемы (2026-08-30): каждый крупный элемент продукта —
центр, блок, контур (примеры из Schoolium: УТЦ — учебно-тематический центр,
КПЦ — контингентно-персональный центр, контур доступа) — несёт **один документ-паспорт**,
в котором собрано всё, что нужно знать об элементе, чтобы работать с ним, не
раскапывая код: функции, состояния, экраны с рендерами, права ролей.

Паспорт — процедурная форма поверх FLOR-ADS: он не заменяет канонические файлы
§3 (`03-runtime.md`, `06-security.md`), а является **единственным домом фактов
блока** (П-5), на который канонические файлы ссылаются. Обратное — пересказ
паспорта в runtime/security — дубль и дефект.

---

## 1. Где живёт

`docs/blocks/<элемент>.md` в репозитории продукта — по одному файлу на элемент.
Права ролей, выведенные из функций элементов, собираются в `docs/roles/<роль>.md` —
по одному файлу на роль. Направление вывода одно: **роль ссылается на функции
элементов, не наоборот** — при изменении функции паспорта роль пересобирается,
а не расползается.

Заголовок — по §7.1 стандарта (id, title, status, owner, last_reviewed).

## 2. Обязательные разделы паспорта

| Раздел | Что в нём | Форма |
|---|---|---|
| **Назначение** | зачем элемент существует, 3–5 предложений, граница с соседними элементами | проза |
| **Функции** | что элемент умеет: каждая функция — строка с идентификатором `F-N`, субъектом (какая роль запускает) и результатом | таблица |
| **Состояния** | конечные автоматы элемента: матрица переходов и матрица полноты по §5.6 стандарта; каждое состояние называет экран, на котором оно видно | матрицы |
| **Экраны** | каждый экран элемента: идентификатор из реестра экранов продукта, маршрут, элементы (кнопки/поля с testid), пустое состояние, состояния ошибок | таблица + рендеры |
| **Права** | матрица «роль × функция» (✎ исполняет / 👁 видит / — нет); каждая клетка ✎ называет право из каталога прав продукта | матрица |
| **Контракты** | эндпоинты и события, которыми элемент говорит с внешним миром — ссылками на файлы контрактов (§5.11–5.12), не пересказом | список ссылок |
| **Проверки** | какие исполняемые ворота стерегут инварианты элемента (П-4); чего не хватает — строкой в реестре недостающих | список |

## 3. Рендеры экранов

Желательная часть раздела «Экраны» — изображение каждого экрана и ключевых
кнопок. Правило одно: **рендер генерируется из живого приложения скриптом**
(скриншот прогона e2e/walkthrough), а не рисуется рукой — нарисованный макет
протухает молча, сгенерированный падает в CI вместе с изменившимся экраном.
Пока прогона нет — раздел ведётся текстом, строка о недостающем рендере идёт
в реестр недостающих с условием появления.

## 4. Лёгкость к изменениям

Стандарты экосистемы меняются; паспорт обязан переживать это дёшево:

- **Ссылки вместо копий.** Всё, что живёт в другом месте (контракт, каталог
  прав, реестр экранов), паспорт называет ссылкой. Единственные факты,
  которыми паспорт владеет, — состав функций, привязка состояний к экранам
  и матрица «роль × функция».
- **Идентификаторы стабильны.** `F-N` функций не перенумеровываются; снятая
  функция помечается «снята решением AR-…», номер не переиспользуется.
- **Один элемент — один файл.** Разделение или слияние элементов — решение
  в `decisions/` продукта, не молчаливая реорганизация.

## 5. Порядок заведения

1. Паспорт заводится при первой спецификации элемента — из материалов спеки,
   а не после реализации (П-3: контракт раньше кода).
2. Изменение функции/состояния/права проходит через паспорт **в том же
   изменении**, что и код: разъехавшийся паспорт — дефект изменения, не
   документации.
3. Файл роли (`docs/roles/`) пересобирается при каждом изменении матрицы прав
   любого паспорта — это выведенный документ, конфликт в нём решается в пользу
   паспортов.
