# Сборка в конвейере, отладка в кодспейсе

Раздел фиксирует решение владельца о разделении контуров: **сборка — в конвейере,
отладка — в кодспейсе.** Здесь: обоснование решения, механизм одного образа для
обоих контуров, воспроизводимое поднятие зависимостей и путь создания кодспейса
агентом.

Нормативная база: П-7 — результат только со ссылкой на зелёную проверку;
FLOR-ADS §5.21 — онбординг до работающего окружения без вопросов; какие проверки
конвейер обязан гонять — `guides/gates.md`.

---

## 1. Правило

**Сборка, результат которой кому-либо передаётся, выполняется только конвейером.
Персональная машина и кодспейс — контур отладки; их результат не передаётся
и не публикуется.** Решение владельца, зафиксировано настоящим разделом.

Обоснование — не вкус, а три свойства, которых у персональной сборки нет
по построению:

1. **Запуск привязан к коммиту.** Конвейер запускается состоянием репозитория;
   персональная сборка — состоянием машины, в котором участвуют незакоммиченные
   правки, глобальные пакеты, переменные окружения и кэш — ничто из этого
   не записано и не воспроизводимо.
2. **Лог существует и адресуем.** На «у меня собиралось» нельзя сослаться;
   на прогон конвейера — можно, и П-7 требует именно ссылки.
3. **Артефакт связан с логом и коммитом.** Артефакт конвейера отвечает
   на вопрос «из чего это собрано»; артефакт с ноутбука — нет. Артефакт без
   такой привязки для экосистемы не существует.

Отладка при этом остаётся быстрой и интерактивной — для неё и существует второй
контур. Разделение не иерархия («настоящая» сборка против «игрушечной»), а
разделение ответственности: контур отладки отвечает на «почему не работает»,
контур сборки — на «что мы передаём».

---

## 2. Один образ для обоих контуров

«У меня собиралось» и «в CI собралось» обязаны означать **один и тот же образ**.
Механизм — спецификация Dev Containers (прочитана из репозитория
`devcontainers/spec`): окружение описывается метаданными в
`.devcontainer/devcontainer.json` (канонические расположения — из спецификации),
и «users can create multiple environments from the same configuration metadata» —
среда пересоздаваема из одного описания, а не настраивается руками.

Оба контура читают этот один файл:

- **Кодспейс** читает `devcontainer.json` нативно: у эндпоинта создания
  кодспейса есть параметр `devcontainer_path` (подтверждено описанием API,
  раздел 4).
- **Конвейер** собирает и выполняет команды внутри того же контейнера через
  экшен `devcontainers/ci` (README прочитан): `runCmd` выполняется в собранном
  dev-контейнере; поддерживается пребилд образа (`imageName`, `cacheFrom`,
  `push`) — конвейер и кодспейс тянут один пребилд вместо повторной сборки.

Дрейф контуров при этом не «запрещён словами», а невозможен без правки одного
общего файла — правка видна в диффе и проходит ревью.

---

## 3. Зависимости контура отладки

База, брокер и прочие зависимости отладки поднимаются **скриптом из
репозитория** — compose-файлом или его обёрткой, — никогда руками. Причина
та же, что в разделе 1: состояние, настроенное руками, не записано; отладка
на нём недоказуема и невоспроизводима — «у меня воспроизводится» перестаёт
что-либо значить. Спецификация Dev Containers прямо оговаривает окружение
как контейнер разработки «along with any needed side-car containers»
с Docker Compose как поддерживаемым оркестратором — зависимости входят
в то же описание среды.

Требования к скрипту зависимостей:

- **данные** — сидом из репозитория: пустая база или воспроизводимый набор,
  но не «та, что была у меня со вчера»;
- **готовность** — healthcheck'ом, а не sleep'ом: сервис объявляет себя живым
  проверкой, зависящие ждут её;
- **сброс** — одной командой в исходное состояние (`down -v && up`), потому что
  невоспроизводимый после экспериментов контур — это снова ручное состояние.

## 4. Как агент создаёт кодспейс

Проверено в этой сессии, а не принято на веру. `docs.github.com` из сессии
недоступен (egress-прокси), поэтому проверка выполнена по машинному описанию
REST API из официального репозитория `github/rest-api-description` — источнику,
из которого генерируется сама документация.

**Чего нет.** CLI `gh` в сессии отсутствует (`which gh` — пусто; проверено).
GitHub MCP-сервер инструментов для кодспейсов не имеет (поиск по инструментам
сессии — ни одного; проверено).

**Что остаётся — REST.** Эндпоинт `POST /user/codespaces` существует
(operationId `codespaces/create-for-authenticated-user`); из описания
подтверждено:

- тело требует `repository_id` **или** `pull_request` — «but not both»;
- полезные параметры: `ref` (ветка), `devcontainer_path`, `machine`,
  `working_directory`, `idle_timeout_minutes`, `display_name`,
  `retention_period_minutes`, `geo` (заменяет `location`, который «closing
  down»);
- токен: «OAuth app tokens and personal access tokens (classic) need the
  `codespace` scope» — область `codespace` подтверждена;
- `enabledForGitHubApps: false` — токен установки GitHub App **не годится**;
- успех — `201`/`202`; типы машин перечисляются эндпоинтом
  `/repos/{owner}/{repo}/codespaces/machines`.

Рабочий вызов:

```bash
curl -sS -X POST https://api.github.com/user/codespaces \
  -H "Authorization: Bearer $GH_CODESPACE_PAT" \
  -H "Accept: application/vnd.github+json" \
  -d '{
    "repository_id": <id из GET /repos/{owner}/{repo}>,
    "ref": "<ветка>",
    "devcontainer_path": ".devcontainer/devcontainer.json",
    "idle_timeout_minutes": 30
  }'
```

**Открытые узлы** (по `guides/open-nodes.md`; реализация пути агент→кодспейс
на этих поверхностях остановлена):

| # | Узел | Решатель | Что остановлено |
|---|---|---|---|
| BD-1 | Годится ли fine-grained PAT: прочитанное описание называет только OAuth и classic PAT со scope `codespace`; про fine-grained оно молчит, а докс-сайт из сессии недоступен | Владелец — живым вызовом с fine-grained токеном | Выбор типа токена для агентов |
| BD-2 | Выдача агенту PAT(classic) со scope `codespace`: секрет, его хранение и срок — решение владельца | Владелец | Автономное создание кодспейсов агентом |

## 5. Шаблон

Минимальный состав двух контуров; полные рабочие файлы несёт `golden-path/`.

```jsonc
// .devcontainer/devcontainer.json — один файл на оба контура
{
  "name": "<проект>",
  "build": { "dockerfile": "Dockerfile" },
  "features": {},
  "postCreateCommand": "make deps-up"   // зависимости — скриптом из репозитория
}
```

```yaml
# .github/workflows/ci.yml — сборка в том же контейнере
- name: Build & test in dev container
  uses: devcontainers/ci@v0.3
  with:
    cacheFrom: ghcr.io/<org>/<repo>-devcontainer
    push: never
    runCmd: make build test
```

```yaml
# compose.yaml — зависимость отладки: сид и healthcheck, не руки и не sleep
services:
  db:
    image: postgres:16-alpine
    volumes: ["./scripts/seed.sql:/docker-entrypoint-initdb.d/seed.sql"]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 2s
      retries: 15
```

## 6. Проверка

Исполняемая проверка «оба контура читают один файл» — в валидаторе
`golden-path/`:

```bash
#!/usr/bin/env bash
# build-debug-check: контуры сборки и отладки читают один devcontainer
set -euo pipefail
status=0
[ -f .devcontainer/devcontainer.json ] || [ -f .devcontainer.json ] \
  || { echo "нет devcontainer.json — контур отладки не описан"; status=1; }
grep -rqs 'devcontainers/ci' .github/workflows/ \
  || { echo "конвейер собирает вне dev-контейнера — контуры разошлись"; status=1; }
exit $status
```

**Недостающие проверки** (П-4, с условием появления):

| Что не ловится | Почему | Условие появления |
|---|---|---|
| Фактическая идентичность образа (кодспейс и конвейер собрали одинаково) | Требуется пребилд в реестре и сверка дайджеста в обоих контурах | Заведение пребилда (`devcontainers/ci` с `push`) в первом продукте; сверка дайджеста добавляется тем же изменением |
| Данные сид-скрипта дрейфуют от схемы | Семантическая связь сид ↔ миграции | Прогон сид-скрипта в конвейере на каждом изменении схемы — вместе с конвейером `golden-path/` |

## 7. Разобранный случай: два контура EduStore

**Что уже правильно.** Конвейер EduStore (`.github/workflows/ci.yml`) собирает
и доказывает по-настоящему: job `flow-smoke` поднимает Postgres сервисом
конвейера, гоняет G-проверки на живой базе (`flow:check` — 25 интеграционных
проверок, `tenant:check` и далее) и складывает артефакты прогона
(`upload-artifact`) — запуск коммитом, лог, артефакт с привязкой: все три
свойства раздела 1 в наличии. Контур отладки поднимается скриптом из
репозитория: `docker-compose.yml` в корне — «postgres + asr + api + web,
bind-mount репозитория», с healthcheck-зависимостью от базы; G-скрипты
поднимают реальный Nest-контекст с реальной базой, а не моки.

**Что дефект.** Одна и та же зависимость описана дважды: Postgres задан
и в `docker-compose.yml` (отладка), и в блоке `services:` конвейера — два
описания одного факта, которые ничто не держит в согласии (образ сегодня
совпадает — `postgres:16-alpine`, — но совпадение держится вниманием, а не
механизмом). И ни один контур не читает `devcontainer.json` — его в репозитории
нет: рантайм разработчика (локальный Node) и рантайм конвейера (`setup-node`
на раннере) совпадают только по номеру версии, а не по образу.

**Как выглядит правильно.** Один `devcontainer.json`; конвейер переходит на
`devcontainers/ci`; описание Postgres живёт в одном compose-файле, который
читают оба контура. Проверка раздела 6 на текущем EduStore честно красная —
она и обозначает объём работ.
