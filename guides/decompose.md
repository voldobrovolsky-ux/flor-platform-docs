# Разбор пришедшего материала

Пришедший материал — монолитный PRD, ТЗ, переписка, результат исследования, чужой
документ — не является документацией. Это сырьё. Раздел описывает, как разложить
его по разделам, ничего не потеряв и не приняв мнение за факт.

Нормативная база: FLOR-ADS §3–4 — куда какой факт кладётся в проекте, §5.7 —
оформление решений, §7 — заголовок и статусы. Выбор уровня и файла —
`guides/doc-levels.md`. Написание целевой спецификации — `guides/write-spec.md`.

---

## 1. Правило

**Разобранный материал перестаёт быть источником истины.** Каждый его факт
переносится ровно в один целевой раздел, каждое решение — в реестр со статусом,
каждое неизвестное — в узлы, остаток объявляется явно. Исходник после разбора
обязан нести пометку, куда переехало содержание, — либо явную пометку
«не нормативен». Материал, лежащий в репозитории без такой пометки, будет
прочитан как действующий документ — независимо от намерений положившего.

---

## 2. Почему разделы режутся именно так

Документация Flōr читается не целиком, а по указанию маршрутизатора — раздел
загружается тогда, когда нужен задаче. Отсюда три требования к целевому разделу,
и они подтверждаются практикой агентных инструкций (документация Claude Code
о памяти агента, прочитана):

- **Один файл — одна тема.** «Each file should cover one topic, with a descriptive
  filename» — правило организации инструкций для агента; смешение тем заставляет
  грузить лишнее.
- **Короче — надёжнее.** «Longer files consume more context and reduce adherence»:
  длинный файл не просто дорог — ему хуже следуют. Норма Flōr — 200–400 строк
  на раздел; больше — раздел делится.
- **Конкретно — значит проверяемо.** «Write instructions that are concrete enough
  to verify»: «Use 2-space indentation» вместо «Format code properly». Тот же
  принцип, что П-6 для архитектурных правил.

И четвёртое, внутреннее: раздел читается в одиночку. Формулировки «как сказано
выше» запрещены — читатель предыдущего раздела не видел.

---

## 3. Процедура

**Шаг 1 — инвентаризация.** Зафиксируй: что пришло (тип, объём, автор), какова
претензия материала — описание существующего, требование, принятое решение,
исследование, мнение. Претензия определяет строгость разбора: чужое «принято»
без подтверждения владельца Flōr — не принято.

**Шаг 2 — классификация утверждений.** Каждое значимое утверждение получает класс:

| Класс | Признак | Куда идёт |
|---|---|---|
| Факт | Есть источник класса A либо это наблюдаемая практика Flōr | В целевой раздел, со ссылкой |
| Решение | Названо решением **и** подтверждено владельцем | В реестр решений; с триггером FLOR-ADS §5.7 — отдельным ADR |
| Мнение | Утверждение без источника и без подтверждения | В нормативный текст не идёт; либо в узел («проверить»), либо в отход |
| Вопрос | Прямо задан или вскрылся при чтении | В реестр узлов (`guides/open-nodes.md`) |

Точка решения: сомнение между «факт» и «мнение» решается в пользу мнения.
Догадка, оформленная как факт, — самый дорогой дефект (П-1): при следующем
чтении она неотличима от факта.

**Шаг 3 — адресация.** Для каждого фрагмента определи целевое место: уровень —
по процедуре `guides/doc-levels.md`, файл внутри проекта — по FLOR-ADS §3–4.
У фрагмента ровно один адрес (П-5); фрагмент, который просится в два места, —
это два фрагмента, раздели его.

**Шаг 4 — перенос.** Пиши целевой раздел по правилам раздела 2: одна тема,
200–400 строк, самодостаточность, конкретность. Перенос — не копирование:
формулировки приводятся к проверяемым, модальность («обязан»/«следует»/«может» —
FLOR-ADS §1.1) проставляется явно, каждое «обязан» получает проверку или строку
в недостающих (П-4).

**Шаг 5 — судьба исходника.** Два законных исхода:

- разобран полностью → исходник получает `status: Superseded` и таблицу
  «что куда переехало» в шапке;
- сохраняется как исследовательский артефакт (сырьё для будущих разделов) →
  в шапке явная пометка «не нормативен; нормативные выводы — в <раздел>».

Удалять исходник молча запрещено; оставлять без пометки — тоже. Точка решения:
если исходник противоречит целевому разделу, побеждает целевой раздел, а
противоречие фиксируется строкой в его тексте — иначе следующий читатель
исходника вернёт устаревшее.

**Шаг 6 — сверка остатка.** Пройди материал ещё раз: всё, что не перенесено
и не объявлено отходом, — потерянное. Ведомость (раздел 4) обязана сойтись:
каждый фрагмент имеет исход.

## 4. Шаблон: разборочная ведомость

Ведётся в изменении, которым выполняется разбор; после — прикладывается
к исходнику или к описанию изменения.

```markdown
## Разборочная ведомость: <имя материала>

Претензия материала: <описание | требование | решение | исследование | мнение>
Автор и происхождение: <кто, откуда>

| Фрагмент (строки/раздел) | Класс | Целевой раздел | Исход |
|---|---|---|---|
| §2 «Протоколы» | факт | docs/06-security.md | перенесён |
| §4 «Надо взять X» | мнение | — | узел: проверить X |
| TL;DR, п.3 | решение | decisions/ADR-000N | подтверждён владельцем, оформлен |
| §7 «Планы» | вопрос | реестр узлов, N9 | заведён |

Остаток (объявленный отход): <что и почему не переносится>
Судьба исходника: Superseded → <ссылки> | не нормативен, сырьё для <...>
```

## 5. Проверка

Исполняемые проверки самодостаточности и размера целевых разделов — запускаются
на каталоге документации:

```bash
#!/usr/bin/env bash
# decompose-check <каталог>: разделы самодостаточны и не разрослись
set -euo pipefail
d="${1:-.}"; status=0
# 1. запрещённые отсылки: раздел читается в одиночку
#    (упоминание правила в «ёлочках» — цитата, не нарушение)
hits=$(grep -rnE 'как (сказано|описано) выше|см\. выше' --include='*.md' "$d" \
  | grep -v '«[^»]*выше[^»]*»' || true)
if [ -n "$hits" ]; then
  echo "$hits"; echo "отсылка к контексту, которого у читателя нет"; status=1
fi
# 2. раздел больше 400 строк — делится (нормативные стандарты в standards/ вне лимита)
while read -r n f; do
  case "$f" in */standards/*|итого|total) continue;; esac
  [ "$n" -le 400 ] || { echo "раздел разросся: $f ($n строк)"; status=1; }
done < <(wc -l $(find "$d" -name '*.md' -not -path '*/node_modules/*') | sed '$d')
exit $status
```

Проверка входит в валидатор золотого пути (`golden-path/`).

**Недостающие проверки** (П-4, с условием появления):

| Что не ловится | Почему | Условие появления |
|---|---|---|
| Мнение, перенесённое как факт | Классификация семантическая | Не автоматизируется; держится ручным ревью по ведомости и полем `sources` в шапке раздела — пустое `sources` при нормативных утверждениях видно глазами |
| Исходник без пометки о разборе | Машине не отличить сырьё от документа | Валидатор `golden-path/` начнёт требовать YAML-заголовок у каждого `*.md` в `docs/` — файл без заголовка станет виден; условие: заведение валидатора |

## 6. Чего в этом разделе нет

`guides/open-nodes.md`. Требования к содержанию проектных файлов — FLOR-ADS §5.
