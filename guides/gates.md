# Гейты: что блокирует изменение и какой проверкой

Раздел отвечает на два вопроса: почему изменение не проходит проверки и что
с этим делать. Перечень гейтов и их сила по тирам — норма FLOR-ADS §9; здесь —
процедурный слой: как каждый гейт запускается локально, как диагностируется
красный, что запрещено делать с проверкой и какие гейты пока не существуют.

Раздел написан по результатам аудита FLOR-ADS §9 (раздел 6 ниже); найденные
дефекты стандарта вынесены в экосистемное решение `decisions/ADR-0001` —
до его принятия стандарт действует как есть.

---

## 1. Правило

**Изменение блокируется только объявленным гейтом, и каждый гейт — исполняемая
проверка, запускаемая локально той же командой, что и в конвейере.** Красный
гейт чинится изменением кода или документов — либо явным решением меняется
правило (с правкой его источника), но проверка никогда не «подгоняется» под
проходящий результат. Зелёный результат принимается только ссылкой на прогон
(П-7); «у меня проходит» без ссылки — заявление.

---

## 2. Карта гейтов и их локальный запуск

Сила каждого гейта по тирам (блок / предупреждение / —) объявлена в FLOR-ADS §9
и здесь не переписывается (П-5). Ниже — исполнительная сторона: чем гейт
реализуется. Валидатор — `golden-path/validator/check-docs.sh`, запускает все
доступные проверки разом; отдельные проверки можно гонять точечно.

| Гейт (по §9) | Чем реализуется | Локальный запуск |
|---|---|---|
| Файлы «О» из матрицы §4 присутствуют | Валидатор: сверка дерева с матрицей по тиру из `catalog-info.yaml` | `check-docs.sh --structure` |
| `catalog-info.yaml` валиден и заполнен | Валидатор: обязательные поля, явная пустота списков | `check-docs.sh --catalog` |
| TechDocs собирается, ссылки целы | Сборка TechDocs + проверка внутренних ссылок | `mkdocs build --strict` |
| Заголовок валиден, не `Draft` для «О» | Валидатор: YAML-шапка каждого `docs/*.md` | `check-docs.sh --headers` |
| `openapi.yaml` / `asyncapi.yaml` валидны | Схемная валидация контрактов | `check-docs.sh --contracts` |
| Контракт без записи в `CHANGELOG.md` | Дифф-проверка одного изменения | `check-docs.sh --increment` |
| Ломающее изменение без ADR | **Недостающая** — см. раздел 5 | — |
| Совместимость схем событий | **Недостающая** — см. раздел 5 | — |
| Верификация потребительских контрактов | **Недостающая** — см. раздел 5 | — |
| Фитнес-функции из `09-testing.md` | Команды из таблицы фитнес-функций проекта | по строке таблицы проекта |
| Поле `personal` вне `05-data.md` | **Недостающая** — см. раздел 5 и Д-3 | — |
| Новый алерт без ранбука | **Недостающая** — см. раздел 5 | — |
| `last_reviewed` просрочен | Валидатор: сравнение даты с лимитом тира (§7.3) | `check-docs.sh --freshness` |

Ломающее изменение определяется по FLOR-ADS §8.1; определение согласовано
с прочитанной спецификацией SemVer 2.0.0: мажорная версия обязана расти при
любом обратно несовместимом изменении публичного API — «MAJOR version when you
make incompatible API changes».

## 3. Процедура: изменение не проходит

**Шаг 1 — прочитай, какой именно гейт красный.** Не «CI упал», а имя проверки.
Имя ведёт в строку таблицы раздела 2, строка — в способ локального запуска.

**Шаг 2 — воспроизведи локально** той же командой. Не воспроизводится — сначала
докажи расхождение окружений (лог конвейера против локального лога), потом чини;
чинить невоспроизведённое — гадание (П-1).

**Шаг 3 — определи, что неправо.** Точка решения с тремя исходами:

- **Неправо изменение** (обычный случай) → чини код или документы, гоняй
  локально до зелёного, пуш.
- **Неправо правило** — гейт ловит то, что по решению владельца ловить
  не должен → правило меняется у своего источника: строка §9 — через
  экосистемное решение (`decisions/`), проектная фитнес-функция — правкой
  её строки в `09-testing.md` с ADR при отклонении от стандарта. Проверка
  правится **после** правки правила, тем же изменением.
- **Неправа проверка** — правило верно, реализация проверки ловит лишнее
  или пропускает → дефект валидатора: чинится в `golden-path/`, изменение,
  вскрывшее дефект, ждёт починки, а не обходит её.

**Шаг 4 — запрещённые исходы.** Отключить проверку, пометить тест пропущенным,
сузить область запуска, закоммитить «временно без проверки» — всё это подгонка.
Единственный законный способ ослабить гейт — явное решение по маршруту шага 3.

**Шаг 5 — готовность к мержу** сверяется перечислением FLOR-ADS §10.1; зелёные
гейты — необходимое условие, не достаточное.

---

## 4. Шаблон: отчёт о красном гейте

Для случая, когда починка не укладывается в само изменение (исход «неправо
правило» или «неправа проверка»), — комментарий в изменении:

```markdown
## Красный гейт: <имя проверки>

Воспроизведение: <команда локального запуска> → <ссылка на вывод>
Что неправо: изменение | правило | проверка — <одной фразой почему>
Маршрут: <чиню здесь | решение в decisions/ | дефект golden-path, ссылка>
Изменение: <ждёт | сжато до объёма без красного гейта>
```

## 5. Недостающие проверки

Гейты §9, у которых пока нет исполняемой реализации, — по П-4 каждый держит
условие появления. До появления реализация гейта — ручное ревью по его строке §9.

| Гейт | Чего не хватает | Условие появления |
|---|---|---|
| Ломающее изменение без ADR | Инструмент диффа контрактов и его порог «ломающести» по §8.1 | Выбор инструмента при заведении конвейера `golden-path/`; до этого — ручная сверка диффа контракта с §8.1 |
| Совместимость схем событий | Реестр схем экосистемы (артефакт E5 перечня §6) — не заведён | Появление реестра схем; заявка на него — строка в `MISSING.md` |
| Верификация потребительских контрактов | Брокер контрактов и первый потребитель, публикующий пакты | Первый внешний потребитель контракта (то же условие, что у `standards/versioning.md` в `MISSING.md`) |
| Поле `personal` вне `05-data.md` | Машинного признака «поле — personal» не существует (дефект Д-3 аудита) | Принятие механизма аннотаций классификации в `decisions/ADR-0001` |
| Новый алерт без ранбука | Алерты как код в репозитории проекта | Первый проект с алертами в репозитории; проверка — сверка каталога алертов со ссылками на `runbooks/` |

## 6. Аудит FLOR-ADS §9: найденные дефекты

Аудит проведён при выводе гейтов из §9 (условие появления настоящего раздела).
Метод: каждая строка §9 проверена на исполнимость (существует ли способ
запустить), каждая формулировка «обязан» разделов §2, §5, §11 — на наличие
строки в §9. Дефекты пронумерованы; исправление текста стандарта — только через
экосистемное решение (`decisions/ADR-0001`, статус `Proposed` до решения
владельца).

| # | Дефект | Где | Класс |
|---|---|---|---|
| Д-1 | Гейт «заполнен `dependsOn`» неотличим от «зависимостей нет»: пустой список и незаполненное поле выглядят одинаково | §9 ↔ §5.2 | формулировка гейта |
| Д-2 | §2.2 объявляет дефолт «нет аннотации тира → Tier 1», но гейт §9 блокирует мерж без тира — дефолт недостижим в репозитории, живущем по гейтам; область действия дефолта не оговорена | §2.2 ↔ §9 | противоречие |
| Д-3 | Гейт «новое поле класса `personal` отсутствует в `05-data.md`» не машинно-проверяем: у CI нет способа узнать класс нового поля; стандарт нарушает собственное требование проверяемости (§5.5) | §9 | непроверяемая формулировка |
| Д-4 | §5.6 объявляет матрицу полноты условием приёмки, но в §9 нет гейта на парность и полноту матриц — «обязан» без проверки | §5.6 → §9 | обязан без гейта |
| Д-5 | §5.19 обязывает каждое правило зависимостей иметь строку фитнес-функции, но соответствие «правило ↔ строка» не проверяется: гейт §9 лишь запускает существующие фитнес-функции | §5.19 → §9 | обязан без гейта |
| Д-6 | §5.7 обязывает генерировать `decisions/index.md` скриптом — актуальность индекса не проверяется ничем | §5.7 → §9 | обязан без гейта |
| Д-7 | §11 обязывает менять русскую и английскую версии стандарта одним изменением — гейта парности нет; расхождение версий (объявленное §11 приоритетным дефектом) не ловится | §11 → §9 | обязан без гейта |
| Д-8 | Гейты «совместимость схем событий» и «верификация пактов» ссылаются на инфраструктуру (E5, брокер), которой нет; §9 не оговаривает поведение до её появления | §9 ↔ §6 | невыполнимый гейт |
| Д-9 | Гейт «ломающее изменение без ADR» не называет механизм обнаружения ломающести | §9 | пробел реализации |

Д-1, Д-2, Д-3, Д-4, Д-5, Д-6, Д-7 требуют правки текста стандарта — вынесены
в `decisions/ADR-0001`. Д-8 и Д-9 правки текста не требуют: они закрываются
инфраструктурой и инструментами — строки в разделе 5 с условиями появления.
Валидатор `golden-path/` реализует гейты по действующему тексту §9, а парность
`ru`/`en` (Д-7) проверяет в настоящем репозитории уже сейчас — как проверку
валидатора, не как гейт стандарта, до принятия решения.

## 7. Разобранный случай: реестр G-проверок (EduStore)

`EduStore/docs/G-CHECKS.md` — живой реестр гейтов проекта; на нём видно каждое
правило настоящего раздела.

**Гейт — исполняемое доказательство.** Реестр начинается определением:
G-проверка — «исполняемое доказательство инварианта (не „проверено глазами")»,
и «утверждение „работает" принимается только со ссылкой на зелёную G-проверку» —
П-7 в проектной форме. Каждая строка реестра несёт команду локального запуска
(`npm --workspace apps/api run tenant:check`) — тот же принцип, что таблица
раздела 2.

**Запрет подгонки — записан в правилах ведения.** Правило №2 реестра: проверка
падает → мерж запрещён; «чинится код или явным решением меняется АР (с правкой
реестра), но не „подгоняется" проверка». Это шаг 3 процедуры, принятый проектом
дословно.

**Недостающие — с условием, не с обещанием.** G-18 (живой OIDC-цикл) невозможен
без секрета внешней стороны — строка в «Недостающих» с условием «при получении
`FLOR_CLIENT_SECRET` (AR-33)»; G-14 привязан к следующему инкременту. Гейт,
который нельзя завести, не исчезает и не имитируется — он ждёт с названным
условием, как раздел 5 здесь.

**Гейт, который не живёт в CI, — оговорён явно.** G-7 требует живого S3
и потому «остаётся ручным прогоном перед релизом; всё остальное — в CI».
Исключение объявлено в реестре, а не существует молчаливо, — так выглядит
законное отклонение от «каждый гейт в конвейере».

## 8. Чего в этом разделе нет

Сила гейтов по тирам и их нормативный перечень — FLOR-ADS §9. Реализация
валидатора и конвейера — `golden-path/`. Готовность изменения целиком —
FLOR-ADS §10.1. Поведение при встрече вопроса, которого гейт не решает, —
`guides/open-nodes.md`. Сами дефекты стандарта и их исправление —
`decisions/ADR-0001`.
